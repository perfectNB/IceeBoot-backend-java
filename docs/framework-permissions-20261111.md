# 基础管理权限与超级管理员修复

本次修复对应 `V005__framework_permissions.sql`，在既有 V004 后执行，不修改已经发布的迁移及其校验和。

## 权限约定

- 权限名称使用中文操作名，接口路径和 HTTP 方法放在独立字段。
- 接口权限编码按模块、资源、操作命名，并以 `:api` 结尾。每个接口编码唯一，分别绑定一个 HTTP 方法与路径模板。
- 菜单、按钮与接口权限分开存储。既有前端按钮编码继续兼容，接口归入对应资源权限分组。
- 动态接口缺少映射时仍拒绝访问；不使用前端绕过、通配符或“找不到配置就放行”。
- 当前账号菜单、资料、退出等自助接口保留登录校验，不要求后台业务管理权限。

迁移覆盖 219 个受保护入口，包括工作台、基础服务、系统管理、审批流程和智能体控制台。接口目录通过测试资源 `rbac/permission-catalog.json` 与真实 Controller 逐一核对。修改受保护接口时，后续迁移与目录必须同步更新。

## 超级管理员

`admin` 是账号名，`superAdmin` 是超级管理员角色编码；普通管理员角色 `admin` 不等同于超级管理员。

迁移仅为既有、启用且未删除的 `admin` 账号补充有效 `superAdmin` 角色关联，并为该角色补齐全部启用菜单和权限关联。其他用户与角色不会因此获得缺失的管理接口权限。

运行时以当前未删除的用户角色关联和有效角色为准。有效 `superAdmin` 自动拥有所有启用且未删除的菜单、按钮及接口权限，后续新增有效资源也不依赖逐项关联。普通角色仍按授权关系过滤；禁用、删除或撤销角色不会因旧角色缓存继续获得全量权限。业务 Tool 权限检查与拦截器使用同一有效权限来源。

旧 Agent 接口 `/v1/agents` 与 Harness 控制台权限分开迁移。遇到编码碰撞时不将旧接口的普通角色授权转移到新的 Harness 接口；当前控制台原路由的角色关联继续保留。

## 角色授权加载与保存

角色详情仍使用原受保护路由，可通过 `?include=permissions` 或 `?include=menus` 只加载弹框需要的一棵树；省略参数时返回两棵树，保持原调用兼容。页面只在打开弹框时加载，失败时禁止保存并提供重试，保存中禁止重复提交。

角色权限、菜单以当前关联和提交集合的差集更新。同一角色的替换在事务中锁定角色行；未变化不写关联，取消项一次删除，新增项通过一条多值 INSERT 写入。新增资源批量检查，操作人和时间统一填充，避免逐条访问登录存储；失败整体回滚。兼容旧角色快照在事务提交后清理，清理故障不改变已提交的授权结果。

运行时菜单和权限各通过一条查询，同时核实当前有效角色、用户角色关联及资源关联。旧角色资源缓存不再参与鉴权，不能从并发旧快照恢复已经撤销的权限。超级管理员、普通角色的边界及数据库故障拒绝访问的规则保持不变。登录身份只在当前 HTTP 请求内复用；新请求重新验证，退出会清除当前身份快照。

本轮不需要数据库迁移。后端重启后生效。自动化验证使用本地 H2 和模拟 Redis，覆盖 SQL 次数、差量保存、并发替换、事务回滚、身份查询次数、撤权和资源停用；不会修改运行环境中的角色授权。

## 升级与验证

升级前备份 RBAC 相关表。应用启动时在 RBAC 表初始化之后、角色缓存加载之前执行 V004 和 V005。V005 的数据变更与版本记录同事务提交；失败回滚。历史文件发布后不得修改，后续变化使用新版本。

已有运行实例手动升级权限数据后，需要清除本项目的角色菜单、角色权限、用户角色及 URL 权限映射缓存。不要清除登录令牌、微信 ticket、刷新令牌或业务缓存。前端刷新页面或重新登录以获取新菜单及按钮权限。

后端代码升级还需要重启实例，使有效角色校验、统一权限查询及权限状态更新接口的鉴权生效。

执行 `scripts/verify.sh` 检查完整后端；前端执行同名脚本，并对本次修改的页面与语言文件运行 ESLint。回归覆盖新旧数据库、SQL 重复执行、接口目录、权限树、管理员与普通角色边界、禁用和撤销角色、旧 Agent 编码碰撞及菜单图标。运行环境还应使用管理员实际请求工作台、存储桶和支付配置等读接口，确认 HTTP 与业务响应均成功。
