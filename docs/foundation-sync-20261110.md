# 通用基础能力同步

## 基线与范围

目标是 iceeboot 后端的 `20261110-agentscope`，基于本仓库 `master`（`a1610e5`）。在前次通用修复 `318381f` 上继续提取面试帝 `interview-emperor/20261104-mock-interview` 的通用代码；来源提交 `34ee683`，同步时已核对远端。

不合并整个业务分支，不复制任何来源环境配置或凭据。本次仅修改后端；前端页面、数据库菜单和权限数据不从产品环境复制。

## 本次补齐

| 模块 | 同步内容 | 去业务化处理 |
| --- | --- | --- |

来源熔断器的半开状态会放行多个探测，本次改为一个探测。通知已读和用户应用关系使用事务行锁，避免首次安装尚未补唯一索引时并发重复插入。通知编辑可清空定向用户和过期时间。支付回调金额不通过四舍五入接受多余小数；并发更新后的订单查询使用当前读。

导出引入来源的 POI 5.3.0、PDFBox 2.0.37，同时固定 commons-compress 1.26.2，解决 MinIO 引入 1.24.0 导致 Office 导出 NoSuchMethodError 的冲突。测试启用 Java 无界面模式，避免 macOS 测试进程启动桌面图形组件。

## 数据库与部署

存量环境先核对并按部署流程应用 `docs/sql/20261110_foundation_extensions.sql`；文件包含支付扩展字段、通知/已读/用户应用关系三张表和索引说明。不要在实体初始化已补列后重复执行 ALTER；CREATE TABLE IF NOT EXISTS 不会为已存在的表补索引。新环境可先执行该 SQL 的 CREATE 部分，再启动实体初始化。真实数据库没有被本次操作连接或修改。

支付补偿任务默认关闭。完成表结构升级后可配置：

```yaml
iceeboot:
  notifications:
    application-codes: [PLATFORM] # 按需增加自有应用编码，与业务产品无绑定
  pay:
    business-compensation:
      enabled: true
      fixed-delay-millis: 60000
      max-retry-count: 8
      batch-size: 20
    yungou:
      circuit-breaker:
        failure-threshold: 3
        cooldown-millis: 30000
```

应用编码仅划分通知受众，不是工作空间或租户权限。后台通知接口已接入既有动态权限机制，部署时需在自身权限表配置对应 URL 并授权；没有权限记录的 URL 沿用框架原有放行行为。

支付回调为 `/v1/pay/callback`，使用签名认证；其他支付接口仍须登录。回调成功按来源返回 `SUCCESS`。自定义支付策略应保证幂等，外部服务副作用不能由本地订单事务保证只发生一次；失败可手动重试或由补偿任务重试。历史成功订单不自动触发补偿。

导出 PDF 需要中文时，通过 `-Diceeboot.export.pdf.font-path=/path/font.ttf` 或 `ICEEBOOT_PDF_FONT_PATH` 提供可用字体；系统字体不可用时，沿用来源的 ASCII 回退逻辑。

## 验证

回归使用 JDK 21、真实 MyBatis SQL、本机 H2 和模拟第三方服务。覆盖非法及重复支付回调、并发回调只执行一次策略、失败重试、通知受众/过期/已读/编辑、接口权限、Office/PDF 导出和熔断状态。完整构建还执行前次迁移的全部回归。真实厂商测试保持显式开启，未调用真实支付、短信、邮件、OSS 或线上数据库。
